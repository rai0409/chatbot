## Task 1. 現状能力の商用解釈

### このシステムが「できるプロダクト」 [実]

- **社内文書（PDF/Word/Excel/PPT/CSV）を取り込み、出典付きで answer する社内ナレッジ検索＋
  Q&A ボット**。
- **2 つの回答モード**:
  1. 承認済み Q&A 完全一致（決定論的・幻覚ゼロ）＝規程/手順/FAQ に最適。
  2. 根拠付き生成（引用必須）＋**自信が無ければ「わからない」と返すガード**。
- **オンプレ/プライベート設置でデータが外に出ない**運用（クラウド非依存、秘密情報を
  イメージに焼かないことを deploy smoke で証明）。
- **部門/子会社のテナント分離**と API キー単位の認可。
- 単一企業・部門単位の**限定ベータは GO（条件付き）**水準（前レポート群と一致）。

### 逆に「できないこと」（正直に） [実]

- **エンドユーザ向けの本番チャット UI が無い**。あるのは `product-preview` と
  `admin/review` の HTML のみ（`webapi/static/`）。実利用は API/最小ページ止まり。
- **SSO / AD / SAML 連携なし**、管理コンソール（非エンジニア向けテナント/鍵/文書管理）なし。
- **マネージド SaaS 基盤・HA・水平スケールなし**（単一ノード Chroma）。大量同時/大規模未検証。
- アラート/監視は**文書のみで未配線**。ロールバック/デプロイ後 smoke は**手動**。
- クロスエンコーダ再ランクは**既定オフ・未昇格**（モデル未キャッシュ）。
- `production_safe` では LLM 生成回答を無効化＝最も安全な構成は「高精度な検索＋承認回答＋
  非回答」であり、**自由会話 AI ではない**（用途次第で長所にも短所にもなる）。
- 大規模・実日本語業務文書での精度/レイテンシ/コストは**未測定** [不明]。

### 日本企業のどの業務に刺さるか [実根拠＋推]

- **情報システム部門が抱える「社内問い合わせ」削減**（情シス FAQ、申請手順）。
- **製造/技術部門の手順書・技術文書・過去トラブル事例検索**（Excel/PPT 多用＝取込が効く）。
- **規程・コンプラ QA**（承認済み完全一致＝言い切り回答が許される領域）。
- 共通する刺さり所＝**「データを社外に出せない」「間違った回答は許されない」**業務。

### 日本市場の構造的特徴（推定だが一般傾向として確度高め）

- **オンプレ/プライベート/データ越境拒否**の要求が欧米より強い（製造・金融・公共・医療）。

- 「1 部門の特定文書群（規程・手順・FAQ）」に絞った PoC → 効果測定 → 横展開。
- 情シス問い合わせ削減 / コールセンター一次対応削減など**工数削減を金額換算**できる用途。
- セキュリティ部門の承認を取りやすい**オンプレ/閉域**構成。

## Task 5(=OUTPUT 5). その理由（リポジトリ根拠ベース）

- **オンプレ/閉域要求に現コードが最も自然に適合** [実]: `store.py` はローカル
  `PersistentClient`、deploy smoke は「秘密をイメージに焼かない」ことを実証、TLS リバプロ
  参照あり（`docs/operations.md`）。クラウド非依存は製造業の IP/データ越境懸念に直接刺さる。
- **製造業の一次文書は Excel/PPT/PDF** → `document_converters/{xlsx,pptx,docx,csv,pdf}` が
  対応済み [実]。PDF だけの競合より取込で優位。
- **「間違えない」要求にガードが適合** [実]: `too_general` ガード＋承認 Q&A 完全一致で、
  自信が無ければ非回答。誤答が許されない手順/安全領域で導入障壁を下げる。
- **単一ノードで十分な規模感** [実]: 1 部門 500〜5,000 人・1 拠点パイロットなら単一ノード
  Chroma で足り、HA 未対応が当面ブロッカーにならない（限定ベータ GO 条件と整合）。
- **分離は将来の横展開保険** [実]: 部門/子会社展開時にテナント分離が効く（再起動/リストア
  越しの分離維持を `tests/test_durable_multitenant_persistence.py` で検証済み）。
- **金融#2 を避ける理由** [実]: SSO/AD・監査ログ改ざん耐性・HA が現状未対応で、最初の 1 社の
  リードタイムが伸びる。製造#1 の方が「今のコードで売れる」確度が高い。
- 一方で**未測定/未対応の正直な留保**: 本番 UI 不在、実大規模文書での精度/レイテンシ未測定
  [不明]、監視未配線。これらは PoC スコープを「1 部門・限定文書・有人レビュー併用」に絞れば
  吸収可能。

## Task 7(=OUTPUT 7). 次にやるべき実装 Prompt（1 つだけ）

**最小本番チャット UI＋単一テナント向け簡易アクセス制御**を、既存 `/chat`・`/chat/stream`
（`production_safe` プロファイル）の上に薄く載せる実装プロンプト。理由は「売れるか」基準で、
製造業オンプレ・パイロットを成立させる最大のギャップが**エンドユーザが実際に使える画面の不在**
だから（コア機能は揃っている [実]）。

推奨ファイル名: `prompts/claude/product/prompt032_minimal_enduser_chat_ui_for_pilot.md`

満たすべき要件（次プロンプトに盛り込む内容）:

- ゴール: 非エンジニアの社員が使える**最小の本番チャット UI**（質問→出典付き回答→「わからない」
  表示→フィードバック送信）を `webapi/static/` に追加し、既存 `/chat/stream` と `/chat/feedback`
  に接続。`production_safe` 既定・承認 Q&A 経路を活かす。
- 厳守制約: .env を読まない／外部接続なし／本番・既定ベクトルストア非変更／合成データのみ／
  クロスエンコーダ・距離閾値・ガード・テナント認可/分離・レート制限の各セマンティクスを変更
  しない／新規依存なし。
- アクセス制御: 既存 `API_AUTH_*` の枠内で、UI からの簡易ログイン（共有シークレット or
  既存 API キー方式）を**既定オフで**追加。SSO は非目標（別プロンプト）。
- テスト: UI 配信ルートの存在、`/chat/stream` への結線、未認証時の挙動、`production_safe`
  既定の維持、生 API キーが HTML/ログ/レスポンスに出ないこと。
- 検証コマンド・コミット/タグ方針・必須最終出力・三連バッククォート不使用の自己チェックを含める。

> 技術系列の並行必須項目（売る前提だが UI とは別）: prompt030 で表面化した
> `_build_base_where` の複数キー `where` の `$and` 化（非既定テナントのベクトル検索正当性）、
> 監視/アラートの実配線、本番/既定コレクションの安全な取込・昇格。これらは PoC 並行で進める。
