# LLM の上限・モデルの割り当て・バッチ・アラート

使いすぎを防ぎ、誰にどのモデルを使わせるかを、使用量を見て決め、急ぎでない処理を安く回すための仕組みです。

## 1 日の上限（`rag_core/llm_quota.py`）

| 上限 | 意味 |
|---|---|
| `user_daily_calls` | 1 人（呼び出し元）の 1 日の呼び出し回数 |
| `user_daily_tokens` | 1 人の 1 日のトークン（入力＋出力） |
| `tenant_daily_tokens` | 1 テナントの 1 日のトークン |
| `tenant_daily_cost` | 1 テナントの 1 日の費用の概算 |
| `global_daily_cost` | 全体の 1 日の費用の概算（テナント別の値はない） |

- **0 は「上限なし」**。既定はすべて 0（環境変数 `LLM_QUOTA_*` が既定値）。
- 設定は、管理コンソールの「上限とモデルの割り当て」から、**全体**または**テナントごと**に、**理由つき**で変更します（監査ログに残る）。優先順位は、テナントの設定、全体の設定、環境の既定。
  テナントの管理者は、自分のテナントの上限だけを設定できます。全体の上限は全体管理者だけです。
- 「1 日」は、営業時間の設定（`BUSINESS_HOURS_UTC_OFFSET`）の**現地時間の 1 日**です。
- **上限に達すると、次の LLM の呼び出しは、呼ぶ前に断られ、回答は抽出型（原文の抜粋）になります。** 利用者への影響は、LLM 障害時の縮退と同じです。
  採点（`judge`）は上限の対象外です（`LLM_QUOTA_EXEMPT_FEATURES`）。ただし、使った分は数えられます。
- `LLM_QUOTA_WARN_RATIO`（既定 0.8）に達すると、画面に警告が出ます。

### 数え方と限界（正直に）

- 使った量は、使用量のファイル（全ワーカーが書く）から読み、数秒間（`LLM_QUOTA_CACHE_SECONDS`）保持します。各呼び出しは、自分の分をすぐに足します。複数ワーカーでも数秒の誤差で一致しますが、**厳密ではありません**。
  呼び出し 1 回の大きさは呼ぶ前に分からないので、**上限を少し超えることがあります**。
- **「利用者」は、API キーの指紋（SSO なら、本人のセッションの指紋）です。** 1 つのキーを複数人で使っていれば、1 人として数えます。
  呼び出し元が分からないとき（API 認証がオフ）は、利用者ごとの上限は適用されず、テナントと全体の上限だけが効きます。
- 費用はプロファイルの単価（配備ごとの設定）からの概算です。

## モデルの割り当て（`rag_core/llm_assignments.py`）

モデルのプロファイルのファイル（`docs/operations/llm_gateway.md`）に、**ティア**（例：`standard`＝小さなローカルのモデル、`premium`＝大きなモデル）を定義します。
コンソールで、ティアを**全員・テナント・役割・1 人**に割り当てます。**いちばん細かい割り当てが優先**されます（人、役割、テナント、全員の順）。

- 使用量の画面で、誰がどれだけ使っているかを見たうえで、割り当てを決めます。
- 割り当ての変更は**理由必須・監査ログつき**で、全体管理者だけが行えます（どのモデルを使うかは、費用と品質に関わる判断のため）。
- 割り当てを消すと、ファイルのルート（テナントの設定、全体のルート）に戻ります。ファイルにないティア名の割り当ては無視され、画面に警告が出ます。
- 回答キャッシュのキーに割り当ての要約が入るので、割り当てを変えると古い回答は使われません。ただし、キャッシュは利用者をまたいで共有されるので、
  **上位のモデルが作った回答が、下位の利用者に返ることはあります**（費用の漏れであって、正しさの問題ではありません）。
- ここでも「利用者」は上と同じ指紋です。

## バッチ呼び出し（`rag_core/llm_batch.py`）

待つ人のいない処理（評価の採点、夜間の再評価、文書の下ごしらえ）には、2 つの回し方があります。

| 方法 | 内容 |
|---|---|
| 同期（`run`） | 1 件ずつ、ゲートウェイを通して呼ぶ。ポリシー・ブレーカー・上限・使用量がそのまま効く。**ローカルのモデルを含め、どのプロファイルでも使える** |
| プロバイダのバッチ API（`submit` → `poll` → `collect`） | プロバイダの `/v1/files` と `/v1/batches`（OpenAI 互換）に一括で渡し、1 日以内に結果を受け取る。費用が下がる。**プロファイルに `"batch": true` と書いたものだけ** |

- ジョブは小さなファイル（`runs/llm_batch/<ジョブ ID>.json`）で、**テキストは持たず ID だけ**を持ちます。回収時に使用量へ書き（**1 回だけ**）、費用にバッチの係数（`LLM_BATCH_COST_FACTOR`、既定 0.5）を掛けます。係数は仮の値で、プロバイダの価格で確認して設定してください。
- バッチに渡した文章は、プロバイダ側のファイルに残ります。**他の呼び出しと同じく、そのプロバイダに渡してよいデータだけ**に使ってください（ポリシーの確認は同じ）。
- LLM による採点は、`eval/tenant_eval/llm_judge.py` の `build_batch_requests`（依頼を作る）と `judgements_from_batch`（結果を判定にする）でつなげます。
- **プロバイダの実物では未確認**です。公開されている API の仕様どおりに書き、模擬のプロバイダでテストしています。

## アラート（`webapi/alerting.py`）

LLM の呼び出しの回数カウンターから、次の信号が出ます（カウンターがあるときだけ）。

| 信号 | 意味 | 警告 / 重大 |
|---|---|---|
| `llm_error_rate` | 接続先に届いた呼び出しのうち失敗した割合（10 回以上のとき） | 10% / 50% |
| `llm_breaker_open` | ブレーカーが開いていて、呼ばれなかった回数（回答は抽出型） | 1 回 / 100 回 |
| `llm_quota_exceeded` | 上限で断った回数 | 1 回 / 100 回 |

通知（Slack・メール）に送るには、`scripts/monitoring_runner.sh`（`/metrics` の記録とアラートの評価）を定期実行し、通知の連携（`slack` / `smtp`）をオンにします（`docs/operations/integrations.md`）。
