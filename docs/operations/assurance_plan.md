# 「通知と監視」「上限」「質問者の識別」を担保する計画

実装した部分と、実環境・運用で担保する部分を分けて書きます。**コードだけでは担保できないものは、そう書きます。**

## 1. 通知と監視

### 何を担保したいか
(a) サービスが止まったら、見ていない時間でも人に伝わる。(b) LLM の障害・上限・誤りの増加に気づける。(c) 記録が壊れたこと・改ざんされたことに気づける。

### すでにあるもの（実装済み）
| 仕組み | 内容 |
|---|---|
| `/ready`、`/admin/health` | Redis・Postgres・Qdrant の到達性（LLM は含めない。LLM が止まっても縮退で稼働とみなすため） |
| `/metrics`（JSON、`?format=prometheus`） | 回答の種類、エラー、フォールバック、レート制限、認証拒否、**LLM の呼び出し・ブレーカー・上限**の各カウンター |
| `webapi/alerting.py` | 信号ごとの OK / WARN / CRITICAL。今回、`llm_error_rate`、`llm_breaker_open`、`llm_quota_exceeded` を追加 |
| `scripts/monitoring_runner.sh` | `/metrics` の記録、アラートの評価、**監査ログの連鎖の検証**（`KURADEN_VERIFY_AUDIT=true`）、新鮮さの確認。終了コード 0/1/2 |
| `scripts/alert_notify.py` | WARN は Slack、CRITICAL は Slack とメール。**外部連携の 3 層スイッチの対象**（`slack`／`smtp`） |
| コンソール | ダッシュボードの LLM 障害の帯、システム状態、使用量（営業時間内の停止時間）、権限・設定の確認 |

### 足りないもの、担保の方法
| 足りないもの | どうするか | 種類 |
|---|---|---|
| 監視を**定期実行**する仕組み | `monitoring_runner.sh` を cron または systemd タイマーで 5 分ごとに実行する。結果の終了コードで通知を出す | 運用の設定 |
| 通知が**オフ**（既定） | `EXTERNAL_INTEGRATIONS` に `slack`／`smtp` を入れ、コンソールで理由を添えてオンにする。通知先は社内のチャンネル・リレーを使う | 運用の設定 |
| **サービス自体の停止**は、アプリの中から測れない | 外部の死活監視（別のホストから `/ready` を 1 分ごとに確認し、連続失敗で通知）。稼働率（平日 8〜21 時、99.0%）の算定は、この外部監視の記録で行う | プローブと集計は実装済み（`scripts/external_probe.py`、`operations/external_monitoring.md`）。**別ホストへの設置と、プローブの死活を見る外部サービスは運用で必要** |
| 複数ワーカーでは、カウンターとブレーカーがプロセスごと | `METRICS_MULTIPROC_DIR` で合算（実装済み）。ブレーカーの状態は `BREAKER_BACKEND=redis` で共有（実装済み、実 Redis では未検証） | 実装済み |
| 通知の**到達確認** | 月 1 回、テスト通知を出して届くことを確認する（手順書に入れる） | 運用 |
| **バックアップ** | `scripts/backup.sh` の対象に、設定・記録・ゴールデン QA・評価台帳・契約などを追加した（今回）。定期実行と、**別の場所への保管、復元の演習**が必要。記録を含むので、アーカイブの保護（暗号化・アクセス制限）が要る | 実装済み＋運用 |
| 記録・使用量の**ディスクの空き** | ディスク使用率の監視（ホスト側）。保持期限の処理（`POST /admin/records/purge`）を定期ジョブから呼ぶ | 運用 |
| **誰も見ない**問題 | 当番（一次受け）と、WARN／CRITICAL ごとの対応手順を決める | 運用 |

### 検証の方法
- 疑似障害の演習: LLM の接続先を止めて、ブレーカーが開き、回答画面の帯が出て、アラートが WARN になり、通知が届き、復旧で閉じることを確かめる。
- 外部監視の停止の演習: アプリを止めて、通知が出ることを確かめる。

## 2. 上限（利用者別・テナント別・全体）

### 何を担保したいか
使いすぎと費用の暴走を防ぐ。上限に達しても、利用者が困らず（抜粋で答える）、管理者が気づける。

### 実装済み
5 種類の 1 日の上限、理由つきの設定（全体・テナント）、呼ぶ前の拒否、回答の注記、警告（既定 80%）、アラート、使用量の記録（監査と同様に残る）、コンソールの画面（`operations/llm_limits.md`）。

### 担保の方法と限界
| 論点 | 担保の方法 | 限界 |
|---|---|---|
| 超過を防ぐ | 呼ぶ前のチェック。数秒ごとに使用量のファイルを読み直す | 1 回の大きさは事前に分からず、**少し超える**ことがある。複数ワーカーでも数秒の誤差 |
| 費用の正しさ | プロファイルの単価（配備ごとの設定）で概算する | **請求額とは一致しない**。プロバイダの請求との突き合わせ（月次）が要る |
| 上限の値の決め方 | まず**上限なし**（0）で 1〜2 か月の使用量を計測し、利用者別の分布を見て、上位 5% が普通に使える水準＋余裕で決める | 実データが要る |
| 利用者別が効くか | 質問者の識別が確かであること（次節） | **キーの共有では 1 人として数える** |
| 抜け道 | 上限は LLM ゲートウェイの入口で効く。回答生成・書き換え・検証のどれも通る。採点だけは対象外（評価の実行を止めないため） | ゲートウェイを通らない呼び出しがあれば効かない（今は、埋め込みの外部呼び出しが別経路） |
| 外部プロバイダ側の上限 | 各社の管理画面で、**月額の利用上限・アラート**を併用する（最後の砦） | 契約・設定の作業 |

## 3. 質問者の識別の確かさ

### 今の識別が何か
- 質問者は、**API キーの指紋**です。SSO（OIDC）を使うと、**本人の識別子（`sub`）のハッシュ**になり、ひとりにひとつの識別になります（ログインのたびに同じ値）。
- API キーを共有していれば、共有している全員が「同じ質問者」です。API 認証がオフなら、質問者は分かりません。

### 担保の方法
| 段階 | 内容 | 状態 |
|---|---|---|
| 1. 本番は **SSO を必須**にする | `ENTERPRISE_OIDC_ENABLED` と ID 基盤の連携。共有の API キーは、システム間の連携用に限る | 実環境での確認が必要（OIDC の実装はあるが、実 ID 基盤では未検証） |
| 2. **キーの共有をやめる** | 利用者ごと、または部署ごとにキーを払い出す（SSO を使わない構成の場合） | 運用 |
| 3. 識別の**強さを画面に出す** | 記録・使用量の質問者が、SSO の本人か、共有キーかを区別して表示する | 未実装（小〜中） |
| 4. **管理操作の名前**を本人確認に置き換える | 提案・承認・判定・版の有効化の「名前」を、SSO の本人の識別子にする。これで「提案した人は承認できない」が実効性を持つ。二人承認（外部連携のオン）は実装済み（`INTEGRATION_APPROVALS_REQUIRED`）。SSO の本人の識別子があればそれで「同じ人」を判定する | 二人承認は実装済み。名前の本人確認への全面的な置き換えは未実装（SSO の確認が前提） |
| 5. **管理者の認証**も個人単位にする | 今の管理者認証は共有のトークン。SSO のグループ（`OIDC_GROUP_ROLE_MAP`）で管理者を決める | 設定の確認が必要 |
| 6. 利用者への**周知と同意** | 記録の目的、保持、読める人を周知（`operations/records.md`） | 運用（人事・法務） |

### 検証の方法
- SSO で 2 人がログインし、記録の質問者が別になり、同じ人は何度ログインしても同じになることを確かめる。
- 共有キーで 2 人が使った場合に、1 人として数えられることを確かめ、画面の表示（段階 3）で見分けられるようにする。

## 4. 優先順位

1. 外部の死活監視と、`monitoring_runner.sh` の定期実行、通知のオン（半日〜1 日。コードなし）
2. バックアップの定期実行と復元の演習（コードは今回で完了）
3. SSO の実環境での確認と、本番での必須化（質問者・管理者の識別の土台）
4. 使用量を 1〜2 か月計測してから、上限と割り当てを決める
5. 識別の強さの表示、名前の本人確認への置き換え（二人承認は実装済み）
6. （実装済み）ブレーカーの Redis 共有。複数ワーカーにするとき `BREAKER_BACKEND=redis` にする
